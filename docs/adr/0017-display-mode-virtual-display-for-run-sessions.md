# A display mode gives PICO-8 `-run` sessions a private virtual display when the machine has none

Every picopilot capability must work on a machine with no display and no sound card (a server, CI, an agent sandbox). The headless `-x` paths (run screenshots, playtest, export, the label capture) already do. The audio-record paths (`audio record`, `audio render`, `run --record-audio`, all through `Pico8Adapter.record`) cannot use `-x`: headless PICO-8 mixes no audio (ADR-0009). They need a `-run` session, which needs a window. Verified by hand and then through picopilot on a display-less NixOS box with PICO-8 0.2.7: a `-run` session on Xvfb with `SDL_AUDIODRIVER=dummy` records a correct WAV (7.8 s of real samples), because `audio_rec` captures PICO-8's own mixer, not the audio device. So we decided that picopilot provides that display itself, governed by a **display mode**:

- `native`: spawn PICO-8 as-is.
- `xvfb`: always run a `-run` session on a private virtual X display.
- `auto` (default): use the virtual display only when there is no display (no `DISPLAY` and no `WAYLAND_DISPLAY`), otherwise behave like `native`.

It is set by the global `--display` flag, the `PICOPILOT_DISPLAY` env var, or the top-level `"display"` key of `picopilot.json`, in that precedence (the order every picopilot setting uses). incur's MCP transport passes no global flags and loads no config file, so under `--mcp` only `PICOPILOT_DISPLAY` (set in the server's environment) applies. An unknown value is an `invalid-display-mode` error for the commands that use the mode (`run`, `audio record`, `audio render`, `doctor`), never a silent fall back to `auto`; other commands ignore it. Only `-run` sessions consult the mode; the `-x` paths never start a display and never pay its startup cost.

## Considered Options

- **Spawn `Xvfb -displayfd 3` directly (chosen).** The server picks a free display number and writes it back on the fd, so parallel runs never race for a fixed `:99`, and picopilot owns the process: it sets `DISPLAY` for PICO-8 and stops the server (SIGTERM, then SIGKILL) when the run ends, whether by sentinel, backstop, crash or spawn failure. A kill-on-abort hook also kills Xvfb and the PICO-8 process group when picopilot itself exits or is signalled mid-run, so no stray process survives.
- **`xvfb-run` (kept as the fallback).** It is a Debian shell script, not always present, and its `-a` picks a display number by probing (racy between parallel runs). When it is the only thing installed, picopilot wraps the PICO-8 command in `xvfb-run -a`; the script runs inside PICO-8's process group, so ending the run takes Xvfb down too. That end is a SIGTERM to the group first (SIGKILL only after a grace period), because a SIGKILLed Xvfb leaves its `/tmp/.X<n>-lock` and socket behind and `-a` then keeps climbing display numbers.
- **Xvfb plus a PulseAudio/PipeWire null sink (rejected).** The earlier idea note assumed audio needed a virtual sink. It does not: with `SDL_AUDIODRIVER=dummy` the mixer still runs and `audio_rec` still captures, so a second system dependency would buy nothing. picopilot sets `SDL_AUDIODRIVER=dummy` on the virtual display unless the user set `SDL_AUDIODRIVER` themselves.
- **Always virtual on Linux (rejected).** It would ignore a working desktop and pay Xvfb startup on every developer machine; `auto` only does it when needed, and `xvfb` exists for whoever wants it anyway.
- **A silent timeout when nothing can provide a display (rejected; this was the old behaviour).** A `-run` session that needs a display, has none, and finds no Xvfb now returns a structured `display-unavailable` error whose message and CTA name the fix (install Xvfb, or run under a desktop).

## Consequences

- The PICO-8 child now inherits the parent environment, overlaid with the values a command resolved (`PICO8_PATH`, `PATH`). It used to receive only that parsed subset, so a `-run` session never saw `DISPLAY`, `WAYLAND_DISPLAY`, `XAUTHORITY`, `HOME`, `XDG_RUNTIME_DIR` or `SDL_*`, and could not open a window or audio device anywhere, even on a desktop. The overlay is a pure function of an injected parent env, so tests still control it. When `XDG_RUNTIME_DIR` is absent, PICO-8 gets a private one (SDL otherwise logs that it is invalid). The same overlay (`engine/child-env.ts`) now applies to shrinko8, whose `pip install --user` copy is only found when HOME reaches the child.
- The record harnesses inline `#include` directives against the source cart's folder, like the playtest transform does. The harness runs from an isolated temp dir, where the `#include main.lua` of every `picopilot init` cart did not resolve, so the harness failed to load and the run reported no WAV with no reason. Inlining was chosen over writing the harness next to the source cart, which would put a temp file in the user's folder.
- A record that ends without a WAV now says why: `noWavReason` (backstop before the sentinel, PICO-8 exited early, or an empty capture) plus the tail of PICO-8's `log.txt` from the isolated `-home`. The report also names the display it used (`native`, `Xvfb`, `xvfb-run`).
- With `run --record-audio`, a missing display is a `display-unavailable` error for the whole command (the screenshots of the `-x` pass are not returned), the same structured failure as `audio record`. The caller asked for audio, and an `ok` report with `audioCaptured: false` is exactly the silent failure this ADR removes.
- The direct Xvfb is started without `-auth`, so another local user could connect to the private display while a recording runs. It shows only a PICO-8 window for a few seconds, which we accept; pass a generated cookie if that ever matters.
- `log.txt` lives in the `-home` shared by every launch in a picopilot process, so the record path deletes it before launching; `pico8LogTail` is then this run's log. Two recordings running at once in one process (an MCP server) can still interleave theirs.
- `picopilot doctor` reports what a machine can do (PICO-8 found and running headless, its version, shrinko8, the display a `-run` session would get) and lists available and unavailable commands, so an agent asks first instead of discovering limits by failing.
- This builds and replaces the idea note `audio-record-virtual-av-session` (deleted), and amends ADR-0009's "recording needs a real session, manual tier only" consequence: live capture is now automatable wherever Xvfb is installed.
